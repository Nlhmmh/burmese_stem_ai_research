## How the simulation was run and evidence recorded

- **Run the fixed cases.** The simulation was run using [run_simulation.sh](raw/run_simulation.sh) and the [simulation runner](raw/SIM-RUN-01-simulation.test.ts). The runner submitted 55 cases to the root application's real route handlers, services and DAOs. It used live model calls and a separate test database, not prepared model answers. It did not use a browser or public HTTP server.
- **Follow the chosen path.** The script set each question, learner preference, response choice and clarification. A/B/C paths, language-help cases and intended-context cases are recorded in [simulation_cases.csv](simulation_cases.csv). These were scripted learner responses, not responses from real participants.
- **Capture the evidence.** The runner saved the input, handler response, generated text, before/after session data and provider-call count for each step. Provider requests, responses, errors and timing were captured separately. Credential headers were not recorded.
- **Check application behaviour.** Scripted checks compared routes, rounds, saved events and retrieved data with the expected behaviour. The runner's overall success meant that all 55 attempts were recorded. It did not mean that every case passed or that the explanations were correct.
- **Prepare content-review material.** Saved English/Burmese outputs, scores, source checks and rationales were organised for review. Content checking and confirmation are described below, separately from automated application checks.
- **Create readable copies.** The [conversion script](raw/convert_evidence.mjs) groups only the original simulation and provider logs by case. It does not import human assessments, generate answers or decide scores. Each entry keeps its original file and line number. Blank review fields in the original logs remain unchanged. Human judgements and scores are shown separately in the case table.

## How to review a simulation case

Choose one row in the [case table](#case-register), such as SIM04-B. Its **Evidence** column links to the execution JSON and detailed content review. Application behaviour is checked in the JSON. Scientific meaning, Burmese wording and content scores are checked in the review.

- **Read what should happen.** In **Expected result**, read **Technical part** for the response path and saved state. Read **Human judgement part** for the expected meaning and reference links.
- **Check how the case was set up.** Open [the simulation test script](raw/SIM-RUN-01-simulation.test.ts) and find the case and response path. Open its **Readable execution logs** link. Follow `cases → case ID → simulationRecords → record`. Compare `question`, `preferences`, `clarification` and each step's `request` with the case table.
- **Check what the application did.** In the same JSON, read `steps`. Compare `httpStatus`, `response`, `before`, `after` and `providerCalls` with **Technical part**. Check the selected route, round, status and saved events. Provider success alone does not mean that an answer was accepted or saved.
- **Check scientific meaning.** Open the row's **Content review** link in [the detailed review file](simulation_review_evidence.md). Read the exact explanation and follow the references in **Expected result**. Check the facts, intended concept and any misleading analogy. Check English as well as Burmese.
- **Check Burmese wording.** Compare the English and Burmese passages. Look for wrong technical terms, changed meaning, incorrect negation, missing information, unnatural wording and unrelated script. For selected passages, use [the bilingual findings](bilingual_assessment/results.md) and [annotations](bilingual_assessment/annotations.json).
- **Check whether the adaptation helps.** In the same content review, compare the adaptation with the earlier explanation. It should address the chosen difficulty, stay on the active concept and add useful support. Different wording alone is not enough.
- **Check scores and limits.** Compare **Human judgement and score** with the detailed review reasons. Scores mean 2 adequate, 1 limited and 0 material error. Any required 0 means Fail. Otherwise, a required 1 means Partial. `NA` means not applicable or not assessable; adaptation appropriateness is NA for initial content. Read **Limitation** too. Rejected answers are not delivered content, and fade or cap produces no new answer. Keep technical success separate from content quality.

Personal checking of all 91 delivered outputs and the supplementary bilingual findings was confirmed in [the shared protocol](../../00_protocol/evaluation_protocol.md#human-verification-and-ai-assistance). Reported review competence is postgraduate STEM knowledge, native Burmese and advanced English. This does not imply an independent second assessor or live observation of every model call. Demonstrating one recorded case does not rerun or recheck all 55 cases.

### Worked demonstration — SIM04-B, gravity

- **Setup:** open [SIM04-B.json](raw/readable/SIM04-B.json). The question is “What is gravity?” Path B requests another example, then High and Finish.
- **Technical checks:** show `initial`, `medium_skip`, `high`, `finish` and `retrieve`. Another example increases the round to 1. High fades at round 1 with no provider call. The session is completed and can be retrieved. The recorded technical outcome is Pass.
- **Human content checks:** open [SIM04-B's review](simulation_review_evidence.md#review-sim04-b) and [R04, Newton's universal law of gravitation](https://openstax.org/books/college-physics-2e/pages/6-5-newtons-universal-law-of-gravitation). Gravity involves mass, not weight. In the initial Burmese explanation, mass was replaced with weight in one section and wording meaning “in a large group” in another. Language adequacy is 0, so the initial output is Fail.
- **Adaptation check:** the thrown-ball example adds relevant support, but its Burmese wording for “near Earth” is imprecise. Its language score is 1 and its content outcome is Partial. This later output did not replace or repair the saved initial explanation.
- **Explain the result:** “The application followed the expected response path, but scientific and Burmese wording problems were found during content review. The exact passages were checked against the reference, and the scores were confirmed. Technical success was kept separate from content quality.”

## Frozen application oracles versus human judgement

The ambiguity expectation comes from protocol F2, not from a claim that a dictionary proves the learner's intention. An HTTP 422 `AMBIGUOUS_STEM_CONTEXT` with no stored session is a controlled technical outcome; downstream paths are not applicable. A 201 response for an ambiguous query requires human inspection of explicit qualification before F2 can receive a content pass.

Path A: High fades at 0→0 with no provider generation, followed by explicit completion. Path B: Medium/skip creates `another_example` at 0→1, then High fades at 1→1 before completion.
