## Run and scope

RUN-B01-20261001-BOUNDS-01 used B01, a real isolated MongoDB 8.2.6 database and a deterministic provider seam. Same-snapshot barriers exposed two concurrent responses. All BND-01–BND-17 passed. Evidence E014–E017. This evaluates constraints, not educationally optimal support.

## How Codex ran the tests and recorded evidence

Codex ran an evaluation-only Vitest suite against the root application's real services and DAOs. A deterministic replacement was used for the model helper, while persistence used a real isolated MongoDB database. This is state/bounds testing, not live-model evaluation or proof of the best teaching policy.

- **Start the isolated database.** [run_bounds_tests.sh](raw/run_bounds_tests.sh) created a temporary MongoDB directory, allocated a localhost port and ran Vitest with [vitest.bounds.config.mts](raw/vitest.bounds.config.mts). The recorded command and startup attempts are in the [command log](raw/BND-RUN-01-command-log.md).
- **Set the case conditions.** [BND-RUN-01-bounds.test.ts](raw/BND-RUN-01-bounds.test.ts) created artificial sessions. `createAtRound` advanced them through real service/DAO operations. Setup-generated calls were excluded from action counts by taking a counter snapshot immediately before the tested action.
- **Control and count generation.** The test replaced `requestStructuredOutput` with fixed bilingual responses and counted its invocations. DAO wrappers counted response/completion attempts but still called the real database functions. Counts refer to this seam, not external model calls.
- **Force the concurrency condition.** For BND-15 and BND-16, a read barrier made two requests use the same stored snapshot. Both were then released. The test checked one success, one controlled conflict and the final database state. BND-15 recorded two generation calls despite one accepted save.
- **Check corrupt stored-state guards.** BND-17 wrote -1, 0.5 and 3 directly into synthetic documents in the temporary test database. It did not modify a learner or production database. The guard rejected each response before generation or response persistence.
- **Record the evidence.** Assertions ran before each `BND_RESULT` console record. The saved [results JSONL](raw/BND-RUN-01-results.jsonl) contains before/after values, action-only counters and notes. The command log retains the 17/17 test result and earlier startup failures. The runner stopped MongoDB and removed its temporary directory after execution.
- **Format readable evidence.** The [converter](../convert_readable_evidence.mjs) creates one JSON file per case with its original before/after record and counters. Run metadata and the command log stay in [the shared index](raw/readable/index.json). Conversion reads saved files only; it does not run Vitest or MongoDB.

The command log is restored unchanged from the [consolidation archive](../../archive/pre_consolidation_markdown_20261008.zip). The [historical manifest](raw/BND-RUN-01-manifest.sha256) identifies captured versions; hashes of revised report text are not hashes of this editorial update.

## How to review the evidence step by step

- **Choose a case.** Read the starting round/status, submitted choice and expected result. Open its Readable logs link. `caseRegister` is the report entry; `records.boundsResults` is the original saved result.
- **Check the fixture and action.** Open the row's Test setup / checks link. Inspect `createFixture`, `createAtRound`, the learner response and the counter snapshot. Do not include setup calls in the action count.
- **Expand the saved record.** Under `records.boundsResults`, open `record`. Compare `before` and `after`, including `round`, `status`, `adaptations`, `responseEvents` and `latestTransition`.
- **Check generation and writes.** Read `providerCallDelta`, `responsePersistenceAttemptDelta` and `completionAttemptDelta`. A persistence attempt is not necessarily a successful write; confirm the saved state.
- **Check the assertions.** Confirm that the test compares the expected route and state, not only whether the call completed. A saved Pass label alone is insufficient.
- **For concurrency, read both requests.** In BND-15/BND-16, inspect the barrier, success/conflict checks and final counts. BND-15 proves one accepted save under this condition, not one generation call.
- **Read the limitation and command log.** The 17/17 result supports the tested boundaries. It does not establish educational optimality, live-provider costs or all possible workloads.

## Interpretation

Stored adaptations stayed within rounds 0–2. Fade and cap appended events without generation or round increments. Finish remained explicit and idempotent; completed sessions rejected responses. Invalid stored-round fixtures failed before provider or write calls.

BND-15 made two provider calls but admitted one atomic write. The stored-round bound therefore protects persistence, not total provider spending or duplicate generation. BND-16 made no provider call at the cap and admitted one event write. These are tested concurrency conditions, not a guarantee for every deployment workload.

## Shared invariants and preconditions

### Valid-session expectations

- Valid stored sessions use an integer `adaptationRound` from 0 to 2. BND-17 deliberately creates invalid values to test rejection.
- It counts generated, persisted adaptations only.
- Each generated adaptation has a matching round and response event.
- Fade and capped responses append an event but do not increment the round.
- No response creates adaptation round 3.
- High remains `in_progress`; non-High at round 2 is
  `review_recommended`; explicit Finish is required for `completed`.
- Provider-call count agrees with whether generation is permitted.
- Concurrent stale writes do not create duplicate events/adaptations.
